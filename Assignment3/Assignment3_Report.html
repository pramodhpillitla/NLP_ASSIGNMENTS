1. Executive Summary & Problem Formulation

As Large Language Models transition into agentic assistants, connecting them to external enterprise resources, local filesystems, and databases has become paramount. Historically, every AI provider developed proprietary function calling schemas, custom webhook APIs, and ad-hoc plugin formats. This created severe ecosystem fragmentation and high integration friction.

The Model Context Protocol (MCP), open-sourced by Anthropic, addresses this challenge by establishing an open, universal, and bidirectional standard connecting AI models (Clients) with external execution environments and data repositories (Servers). This assignment designs, implements, and validates an enterprise MCP Server for AI assistants over standard I/O (stdio) using JSON-RPC 2.0 protocol specifications.

2. Model Context Protocol (MCP) Architectural Specification

2.1 Client-Server Topology & Transport Primitives

MCP utilizes a decoupled Client-Server architecture. The host application (such as Claude Desktop, Antigravity, or an IDE) operates as the MCP Client, while local or remote microservices act as MCP Servers. Communication occurs over standard streams (stdio) for local isolation or Server-Sent Events (SSE) for remote networks.

All message payloads adhere strictly to JSON-RPC 2.0 specifications:

{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "query_database", "arguments": {"query": "SELECT * FROM metrics"}}}

2.2 The Three MCP Core Primitives

  • 1. Tools (Active Execution): Dynamic executable functions that can be invoked by the model. Each tool defines a strict JSON Schema for input validation and returns structured content arrays.
  • 2. Resources (Passive Context): Passive, readable contextual endpoints addressed by custom URI schemes (e.g. assistant://system_config). Resources supply live data to models without executing code.
  • 3. Prompts (Guided Interaction): Pre-parameterized prompt templates provided by the server to guide user workflows and standardize assistant interactions.

    4. Protocol Lifecycle & Verification Walkthrough

    We developed an automated Python verification client (`mcp_client_test.py`) that executes the complete protocol lifecycle over stdio pipes:

  • Phase 1 - Initialization Handshake: Client initiates handshake with 'initialize' request; server returns capabilities and serverInfo; client acknowledges with 'notifications/initialized'.
  • Phase 2 - Tool Discovery: Client invokes 'tools/list', validating schema compliance against JSON-RPC 2.0 standards.
  • Phase 3 - Tool Execution: Client executes 'tools/call' with arguments; server evaluates SQL, enforces safety restrictions, and returns structured text payloads.
  • Phase 4 - Resource Introspection: Client reads 'resources/read' with target URIs; server returns formatted metadata and payloads.
  • Phase 5 - Prompt Templating: Client fetches 'prompts/get', verifying argument substitution and message structure.

    6. Security & Sandboxing Principles

    Exposing local capabilities to AI models requires strict security boundaries:

  • SQL Injection & Mutation Guard: The database tool rejects any statement containing DROP, DELETE, INSERT, UPDATE, or ALTER, ensuring data immutability.
  • Append-Only Audit Trail: All tool executions and administrative queries are persisted to an append-only SQLite audit log with ISO timestamps.
  • Process Isolation: The server communicates exclusively via stdio pipes, preventing unauthorized external network listeners.
